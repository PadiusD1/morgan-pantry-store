# FRC workflow and reliability audit — October 8, 2026

## Scope and deployment

This audit covers the active React/Vite/Express application in `PadiusD1/morgan-pantry-store`, connected to the `morgan-frc` Vercel project. The baseline was `ef638203acc15bf241710eab610bf081da4ac12c` on `main`. The application uses PostgreSQL through `server/pg.ts`; the older Flask/SQLite repository is not the active deployment.

Work focused on donor creation and receiving, item name entry and barcode scanning, board exports, stock consistency, student requests, desktop/mobile rendering, role permissions, and the production build. All records created by the automated tests belong to isolated synthetic local databases. No real donor, student, inventory, or transaction records were modified by this audit.

## Findings and resulting behavior

| Area | Confirmed problem | Fix and result |
| --- | --- | --- |
| Donors | Donor lists, totals, and history could remain stale after check-in or an uncertain save response. | Invalidate the whole donor query family and donation-source list after relevant saves; publish canonical saved records and reconcile active reads. |
| Donors | A new donor could be hidden by the current search; an existing same-name donor could be reported as newly created even though typed changes were not saved. | Show the saved row, distinguish created/updated/existing outcomes, retain unsaved input, and offer an explicit edit of the existing donor. |
| Donors | Clearing an optional field sent `undefined`, leaving the old database value intact. | Send explicit `null` for cleared contact/details fields and verify persistence after reload. |
| Donor attribution | Legacy name matching could attribute a partner-linked donation to a same-name donor; detail/list aggregation could disagree. | Explicit donor/partner IDs take precedence. Legacy fallback excludes partner-linked transactions and chooses one donor deterministically. |
| Donor history | History/export/detail queries issued a separate item query for every donation and rounded small line values too early. | Load transaction items in one joined history query; retain full numeric precision until presentation. |
| Donor deletion | Deleting a donor with donation history surfaced an opaque database failure. | Return a conflict explaining that the donor should be made inactive to preserve history; show delete controls only to administrators. |
| Partners | Entering a duplicate partner identifier could update the existing organization implicitly. | A create remains a create; a conflict keeps the new form intact and leaves the stored organization unchanged. Contributions prefer stable IDs. |
| Item entry | Normal fast typing could be intercepted as scanner input. | Restrict scanner capture to designated barcode fields/background; preserve normal item, donor and student field typing and keyboard navigation. |
| Item entry | Typing an item name did not provide an effective saved-item selection and metadata-fill path. | Add accessible name/brand/barcode suggestions in Inventory and Check-In, carrying the canonical item ID and saved details. |
| Barcode lookup | Inventory called an external provider directly, conflicting with Vercel's same-origin connection policy. | Use the same-origin server barcode endpoint and publish its canonical item in the inventory cache. |
| Barcode races | Late lookups could overwrite a newer selection; repeated scans could be dropped; a fast scan immediately after mount could lose its leading characters. | Version pending lookups, retain full barcode field values, register capture before paint, and queue repeated scans without arbitrary duplicate suppression. |
| Allergy checks | A freshly looked-up item could bypass an allergy check because the React render held stale inventory. Reopening the warning could put its overlay above the dialog. | Check the resolved item/live cache; put the dialog above its overlay and test cancel, reopen, confirm, and checkout. |
| Board exports | Operational tables were the primary export path and could disclose unnecessary client detail to board recipients. | Add prominent board CSV and Print / save PDF actions with aggregate service, distribution, value, stock and monthly activity figures. |
| Reporting period | Detailed CSV ignored the selected dates; browser and annual reports could use different calendars. | Use one inclusive Baltimore-calendar reporting period for visible totals and detailed exports; keep annual exports explicitly scoped to their selected year. |
| Annual reporting | A multi-item emergency transaction counted as multiple emergency visits; changing prices produced misleading displayed unit values. | Count distinct transaction IDs and calculate weighted historical unit values. Preserve separate inventory IDs even when names match. |
| Reporting failures | Database failures could be shown as zero emergency activity; HTML/sign-in responses could be downloaded as CSV. | Return real failures, show retryable UI states, and validate CSV responses before download. |
| Reporting performance | Operational tables could render every row at once. | Page tables in sets of 50 while keeping every selected row in the export. |
| Data import | JSON restore recreated stock and then replayed movements, risking duplicate stock/records and partial restoration. | Disable the unsafe import with an explanation. Keep downloadable data snapshots; label them accurately rather than calling them complete database backups. |
| Transaction validation | Empty transactions and zero/negative/fractional quantities were accepted by the API. Invalid numeric values could reach PostgreSQL. | Reject invalid data before opening a write transaction; prevent fake visits and movements that reverse stock unintentionally. |
| Checkout stock | Insufficient recorded stock was silently clamped to zero and could consume stock reserved for requests. | Preserve the existing ability to finish checkout, but record any required count increase in `stock_adjustments`, preserve reserved stock, and notify staff to verify the shelf count. No donation is invented to cover the difference. |
| Pickup counts | Completing a pickup with zero distributed items could create a false visit. | Reject empty pickup and keep its request/reservation intact; omit zero-quantity distribution lines. |
| Dashboard navigation | The Ready for Pickup count included approved states that its link omitted. | Add an Awaiting pickup filter covering all three counted states. |
| Checkout atomicity | Mixed item ordering could cause avoidable lock contention; repeated lines and uppercase UUIDs needed consistent handling. | Aggregate normalized item IDs, lock all affected rows in stable order, and commit the movement, adjustment, transaction and retry response together. |
| Student requests | Request, items, audit log and notification were committed separately; the daily-limit check could race. | Save the entire request in one transaction, serialize creation for the same normalized identifier, and count the Baltimore day correctly across daylight-saving changes. |
| Dashboard | The stats endpoint loaded complete history and issued one item query per recent visit; request-count failures were silently replaced with zeros. | Use five aggregate SQL queries, return a real error when data is unavailable, and align dashboard dates with reporting. |
| Connection resilience | An idle database connection error could terminate the server process. | Handle the pool's idle-error event so it can discard the broken connection and reconnect. |
| Sessions | A malformed percent-encoded cookie could throw before authentication's error handling. | Ignore malformed cookies and keep valid sessions working. |
| Storage copy | Settings still described a local SQLite database and CSV backups. | Explain shared persistent records and distinguish data exports from administrator-managed database backups. |

## Using the updated workflows

### Board update

Open **Reports**, choose **This month**, **Last month**, **Year to date**, or custom inclusive dates, then choose **Download board CSV** or **Print / save PDF**. The board summary includes distribution visits, distinct linked clients, units, pounds, estimated value, emergency visits, received stock, current stock, monthly activity, and distributed items.

Client names, student IDs, contact details, donor names and coordinates are excluded from the board files. Operational exports remain available separately to authorized staff. Current stock is explicitly a snapshot at generation time, not reconstructed historical stock. Distinct linked clients are not an estimate of household members or anonymous people served. The report flags unlinked visits and units without a positive recorded weight or value so missing data is visible.

### Receiving and donors

Create the donor, then select that donor as the source during Check-In. Type the item name (or brand/barcode), select the intended saved item, enter the received quantity and save. The item identity remains the same and donor totals/history refresh. When an existing donor name is found, the form explains that result instead of pretending the new details were saved.

### Scanner and checkout

Use the barcode field for hardware scans. Normal text fields remain normal typing fields. Repeated scans queue, late results cannot replace a newer manual selection, and allergy confirmation is part of the checkout flow. If a checkout needs more stock than is recorded as available, the existing nonblocking policy remains, but the correction is recorded and staff are told to verify the physical shelf count.

## Verification

The original baseline passed 372 unit tests despite the reported workflow defects. This update adds behavioral regression tests, actual browser actions, and database-level tests rather than relying on the baseline suite alone.

Local development browser checks have verified all 12 staff routes at 1440-pixel desktop and 390-pixel mobile widths with no document overflow or uncaught page errors. They also exercise real saves, navigation and reload, CSV contents, printable board contents, failures, duplicate handling, stock readbacks, request approval/pickup, authentication and role restrictions.

The committed pipeline in `.github/workflows/frc-audit.yml` runs Node 22, locked dependency installation, TypeScript, unit tests, native PostgreSQL 17 integration tests, the exact Vercel build command, and Chromium tests against the compiled API/frontend with the deployed content-security policy. Browser screenshots and failure traces are retained as GitHub Actions artifacts for 14 days. See [the production test instructions](../scripts/e2e/README.md).

Local browser tests use the PostgreSQL-compatible PGlite runtime because a native PostgreSQL process cannot run under the local executor's user restrictions. Those tests establish functional behavior with persisted synthetic records. They do **not** establish native PostgreSQL locking/concurrency behavior. The separate native PostgreSQL CI suite is the concurrency gate.

Final test counts and deployment status are recorded in the pull request and associated check runs, so this document does not label an unexecuted or failed gate as successful.

## Cost, performance and operating limits

The update keeps the current Vercel/PostgreSQL architecture and adds no paid runtime service. The browser-test dependency is development-only. Joined donor history, SQL aggregation, fewer repeated reads, route-level code splitting already present in the application, and bounded report table rendering reduce avoidable work without a platform migration.

There are still practical limits to plan for:

- The shared repository provider fetches the entire transaction dataset. Table pagination limits browser rendering, but does not yet paginate that API dataset. Before a substantially larger rollout, measure real record counts and response sizes and move report aggregations and history pagination fully to the server.
- Local timing evidence uses synthetic data and a local database; it is not a production latency or monthly-bill measurement. Vercel usage/billing, real cold starts, production query plans and Supabase connection utilization require the relevant account access.
- Existing unlinked legacy donor names are interpreted deterministically. Renaming or changing the status of such donors can still change name-based historical attribution; concurrent legacy writes are not protected by a stable-ID foreign key. Deletion now checks the name-only history currently associated with the donor as well as explicit links. A separately reviewed migration should establish stable donor IDs for historical rows once ambiguous records have been reconciled. No historical production data migration is included here.
- CSV/JSON exports are not a full recoverable database backup. Verify the database provider's backup retention and test restoration to an isolated database. The previous unsafe JSON import stays disabled until a transactional, schema-complete restore is implemented and tested.
- Estimated food values and weights are only as reliable as the recorded item data. The board summary exposes missing measurements rather than silently claiming complete valuation.
- Checkout continues to allow a count correction when recorded available stock is insufficient. If the pantry wants strict stock refusal or explicit pre-checkout approval instead, that is a separate operating-policy change.
- Hardware timing was tested with synthetic keyboard bursts at 2 ms and 60 ms gaps. The physical pantry scanner and printer still need a short onsite acceptance check.
- This is a targeted, evidence-based audit of the app's main workflows. It is not a guarantee that every possible defect, accessibility issue, browser/device combination or production outage has been eliminated.

## Release and rollback

No schema migration or production data rewrite is required by this update; it uses the existing release-one stock-adjustment and request tables. The build command remains driven by `vercel.json`. Deploy through the GitHub-connected Vercel project after required checks pass. If a release needs rollback, restore the preceding Vercel deployment or revert the merge commit; preserve recorded transactions and stock adjustments.
